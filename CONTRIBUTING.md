# Правила работы над проектом

Единый свод правил для всех участников: как добавлять изменения, как вести ветки,
как и когда обновлять документацию, как оформлять коммиты и pull request. Цель —
чтобы код и документация выглядели одинаково независимо от того, кто их пишет.

Если правило здесь расходится с тем, что ты видишь в коде, — приоритет у этого
файла; расхождение стоит починить отдельным изменением.

## Структура репозитория

Репозиторий содержит только приложение оператора (см.
[ADR 0001](docs/decisions/0001-app-only-repository.md)); приложение лежит в корне.

- `lib/` — код приложения, разбитый по фичам.
- `test/` — тесты на фейках, без железа.
- `third_party/` — вендорный форк `flutter_blue_plus_winrt`.
- `docs/` — документация; точка входа — [docs/README.md](docs/README.md).

Карта документации и продуктовое видение — в [docs/README.md](docs/README.md) и
[docs/vision.md](docs/vision.md).

## Ветки и рабочий процесс

```text
main   — стабильная ветка, всегда разворачиваемое состояние
dev    — интеграционная ветка разработки
<тип>/<краткое-описание> — рабочие ветки от dev
```

- Любая работа идёт в отдельной ветке **от `dev`**, не в `dev` напрямую.
- Префиксы веток по смыслу: `feature/...`, `fix/...`, `docs/...`, `chore/...`.
- Изменения попадают в `dev` через **pull request с ревью**, а не прямым push.
- В `main` попадает только проверенное состояние из `dev`.
- Слияния в общие ветки (`dev`, `main`) выполняет владелец соответствующей зоны.
- Меняй небольшими частыми порциями: маленькую задачу проще проверить, влить и
  откатить, и она реже конфликтует.

### Жизненный цикл ветки

Ветка — одноразовое рабочее пространство под одну задачу, а не место хранения.
Долгоживущие только `main` и `dev`; остальные создаются под задачу и удаляются
после merge, поэтому ветки не копятся.

```bash
git switch dev && git pull            # свежий dev
git switch -c feature/<задача>        # ветка под конкретную задачу
# ... коммиты, push, PR в dev, ревью, merge ...
git switch dev && git pull
git branch -d feature/<задача>        # удалить локальную ветку
git fetch --prune                     # подчистить remote-tracking ссылки
```

- Создавай ветку в момент начала задачи от свежего `dev`, а не заранее.
- Не переиспользуй уже смерженную ветку — заводи новую от `dev`.
- Включи на GitHub «Automatically delete head branches», чтобы remote-ветка
  удалялась автоматически при merge PR.
- Периодически чисти локальные влитые ветки: `git branch --merged dev`.

## Документация обязательна вместе с изменением

Документация живёт в репозитории и обновляется в том же PR, что и изменение
(docs-as-code). Правила:

- Изменил поведение или контракт — **обнови соответствующий документ в этом же
  PR**. PR без обновления доков, когда оно требуется, не считается готовым.
- **Один факт — в одном месте.** Не дублируй описание в нескольких доках; вместо
  копии ставь ссылку.
- Куда что писать:
  - продуктовые цели и границы — [docs/vision.md](docs/vision.md);
  - архитектурные решения — `docs/decisions/` (ADR, см. ниже);
  - стабильные контракты (пакет эксперимента, пакет устройства) —
    `docs/reference/`;
  - дизайн по компонентам — `docs/flutter_app/`.
- Контракт всегда первичен: сначала фиксируем контракт в `reference/`, потом по
  нему пишем код и компонентные доки.

## Стиль документации

- Пиши для читателя: ясно, по делу, активным залогом и в настоящем времени.
- **Заголовок документа описывает содержание**, а не имя файла
  (`# Валидация пакета`, не `# validation.md`).
- В начале каждого документа — короткий абзац «что это и для кого».
- Не используем служебные болванки вида `## Статус / Draft`.
- Не нумеруем заголовки вручную (`## 1.`, `## 2.`) — заголовки смысловые.
- Не повторяем заголовок документа отдельным `##` сразу под ним.
- Язык документации — русский; технические идентификаторы, имена файлов и
  команды — латиницей и в `code`-форматировании.
- Markdown: код и деревья — в fenced-блоках, ссылки между доками — относительные,
  без хвостовых пробелов в строках (это проверяет CI).

## Архитектурные решения (ADR)

Значимое архитектурное или контрактное решение фиксируется отдельным ADR в
`docs/decisions/`:

- один файл на одно решение, имя `NNNN-краткое-название.md`;
- секции: «Статус», «Контекст», «Решение», «Последствия»;
- после `Accepted` ADR не переписывается — новое решение оформляется новым ADR,
  который при необходимости отменяет предыдущий.

## Стиль кода

Общий принцип: **новый код пишется в стиле окружающего**. Перед добавлением
посмотри соседние модули и следуй их структуре, именованию и форматированию.
Форматирование оставляем инструменту: следуем `dart format` и линтеру, не спорим
о пробелах и переносах вручную.

- всё сценарное состояние — в BLoC/Cubit; `setState` только для локальной
  визуальной мелочи, не для данных/записи/разметки/навигации;
- слои `presentation → application → domain`, `data → domain`, `platform → data`;
  UI не обращается напрямую к BLE и файловой системе;
- фичи изолированы, каждая со своими `presentation/application/domain/data`;
- внешние зависимости (BLE, файлы, часы) прячем за портами в `domain`, чтобы
  сценарии тестировались на фейках.

## Тесты

- Перед merge все тесты должны быть зелёными.
- Проверки запускаются из корня репозитория:

  ```bash
  flutter analyze
  flutter test
  dart format --set-exit-if-changed lib test
  ```

- Новый функционал сопровождается тестами; для важной логики покрываются и
  сбойные пути (ошибки, обрывы связи, граничные случаи).

## Коммиты

- Сообщение — на русском, англицизмы по минимуму (технические идентификаторы
  латиницей допустимы).
- Формат:

  ```text
  Краткий заголовок в повелительном наклонении

  - что изменено и зачем;
  - ещё один пункт при необходимости.
  ```

- Заголовок — до ~72 символов, без точки в конце.
- Один коммит — одно логическое изменение; не смешивай несвязанные правки.

## Pull request

- Базовая ветка — `dev`.
- В описании PR: **что** изменено, **зачем** и **как проверено** (какие тесты
  прогнаны или какая ручная проверка сделана).
- Чек-лист перед запросом ревью:
  - тесты зелёные;
  - документация обновлена под изменение;
  - нет хвостовых пробелов;
  - затронутые контракты отражены в `docs/reference/`;
  - на архитектурное решение заведён ADR.
- Ревью ведётся по сути и по контракту (помогает ли изменение текущему MVP,
  не ломает ли гарантии), а не по принципу «нравится / не нравится».

### Размер и ревью

- Держи PR **маленьким и сфокусированным** — одно логическое изменение. Маленький
  PR быстрее ревьюится, реже конфликтует и проще откатывается.
- Ревьюер смотрит: дизайн, корректность, сложность, тесты, именование,
  комментарии, документацию и стиль.
- Одобряем, когда изменение **улучшает общее состояние кода**, даже если оно не
  идеально. Необязательные придирки помечаем `nit:` и не блокируем ими merge.
- Ревью — приоритетная задача: на запрос ревью и на комментарии отвечаем быстро
  и по существу.
