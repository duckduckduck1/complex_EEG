# Правила работы над проектом

Единый свод правил: как добавлять изменения, как вести ветки, как документировать,
как оформлять коммиты и pull request. Цель — чтобы код выглядел одинаково
независимо от того, кто его пишет.

Если правило здесь расходится с тем, что ты видишь в коде, — приоритет у этого
файла; расхождение стоит починить отдельным изменением.

## Структура репозитория

Репозиторий содержит только приложение оператора; приложение лежит в корне.
Что это за проект и железо — в [README.md](README.md), формат данных и контракт
с устройством — в [docs/data-format.md](docs/data-format.md).

```text
lib/
  main.dart          точка входа
  main_app.dart      корневой виджет: тема, зависимости, глобальные Cubit
  theme.dart         тёмная тема «Осциллограф» (cyan-акцент, Material 3)
  core/              общее: типы ошибок, модель отсчёта
  features/          доменные фичи: devices, recording, annotation, navigation
  fuetures/          экраны и виджеты: ble_page, main_layout, main_page
  platform/          платформенные адаптеры (ble/)
test/                тесты на фейках, без железа
docs/                формат данных эксперимента
installer/           скрипты сборки установщика
third_party/         вендорный форк flutter_blue_plus_winrt
```

Внутри фичи зависимости идут в одну сторону: `presentation → application →
domain`, `data → domain`. В `domain` живут модели и **порты** — абстракции над
BLE, файлами и часами. Благодаря им сценарии тестируются на фейках без железа и
без диска. UI не обращается к BLE и файлам напрямую; сценарное состояние — в
BLoC/Cubit, `setState` только для локальной визуальной мелочи.

Остальное документируют сами классы — смотри `///`-комментарии, начиная с
`RecordingBloc`, портов в `features/recording/domain/recording_ports.dart` и
`features/devices/domain/ble_adapter.dart`.

> `fuetures/` — опечатка, доставшаяся от прототипа (там же `proccesing_math`).
> Каталог живой; переименование затронет все импорты и пока не сделано.

## Решения, которые не надо откатывать по незнанию

- **Сигнал пишется в двух версиях.** `signal.bin` — после фильтров (с ним
  работают), `signal_raw.bin` — как пришёл с устройства. Фильтр необратим,
  поэтому сырой сигнал храним: по нему можно перефильтровать иначе. Цена —
  ещё ~3,6 МБ в час.
- **Фильтр записи и фильтр графика — разные.** Запись использует потоковый
  Butterworth по одному отсчёту; график перефильтровывает весь буфер целиком и
  для записи непригоден.
- **Обрыв связи → новый сегмент и `gap`, без синтетических отсчётов.** Нули за
  время разрыва не дописываются: дырка честно описана в `gaps`, а поддельный
  сигнал испортил бы спектральный анализ.
- **ФБМ работает только во время записи** и гаснет на остановке и на обрыве —
  чтобы свет всегда был привязан к эксперименту и попадал в его журнал.
- **Метки — про наблюдаемое поведение** (спит, ест, бегает), а не про стадии
  сна. Оператор биолог: по сигналу он ничего не скажет, а поведение в клетке
  опишет надёжно. Скоринг по ЭЭГ — задача постобработки, не оператора.
- **Поиск устройства фильтрует по имени ИЛИ `0xFFE0`.** Требовать оба признака
  нельзя: в первом adv-пакете имени ещё нет, и устройство ищется минутами.
- **Фильтры включены по умолчанию** и на графике, и в диалоге записи. Решать,
  нужен ли режекторный фильтр на 50 Гц, оператору не с чем, а сетевая наводка
  есть всегда: выключенный notch — почти наверняка забытый notch.
- **Анимация графиков выключена** (`duration: Duration.zero`) — иначе живой
  график дёргается.

## Выпуск версии и установщик

1. Поднять `version:` в `pubspec.yaml` — единственный источник правды: номер
   оттуда попадает и в свойства `.exe`, и в имя установщика.
2. Собрать установщик:

   ```powershell
   powershell -ExecutionPolicy Bypass -File installer\build_installer.ps1
   ```

   Скрипт собирает релизную сборку Flutter и отдаёт её Inno Setup; готовый файл
   появляется в `build\installer\`. Нужен
   [Inno Setup 6](https://jrsoftware.org/isdl.php) на машине сборки.
3. Поставить установщик у себя и проверить: программа запускается, устройство
   находится, запись идёт. Последний момент, когда ошибку видно до оператора.
4. Слить в `main`, поставить тег `vX.Y.Z` и приложить установщик к GitHub
   Release.

Почему так, а не иначе:

- **Собранный установщик в репозиторий не коммитим** — он уходит в GitHub
  Releases. Каждая версия бинарника добавляла бы десятки мегабайт в историю git
  навсегда, а очистить историю нельзя.
- **MSIX не используем:** он требует подписи, и без покупного сертификата
  оператору пришлось бы вручную ставить самоподписанный сертификат перед
  установкой — то есть делать ровно то, чего он делать не умеет.
- **Скрипты установщика лежат в UTF-8 с BOM.** Без него Windows PowerShell 5.1
  читает `.ps1` как ANSI и ломается на кириллице ещё до начала сборки.

## Ветки и рабочий процесс

```text
main   — стабильная ветка, всегда разворачиваемое состояние
dev    — интеграционная ветка разработки
<тип>/<краткое-описание> — рабочие ветки от dev
```

- Любая работа идёт в отдельной ветке **от `dev`**, не в `dev` напрямую.
- Префиксы веток по смыслу: `feature/...`, `fix/...`, `docs/...`, `chore/...`.
- Изменения попадают в `dev` через **pull request с ревью**, а не прямым push.
- В `main` попадает только проверенное состояние из `dev`.
- Слияния в общие ветки (`dev`, `main`) выполняет владелец соответствующей зоны.
- Меняй небольшими частыми порциями: маленькую задачу проще проверить, влить и
  откатить, и она реже конфликтует.

### Жизненный цикл ветки

Ветка — одноразовое рабочее пространство под одну задачу, а не место хранения.
Долгоживущие только `main` и `dev`; остальные создаются под задачу и удаляются
после merge, поэтому ветки не копятся.

```bash
git switch dev && git pull            # свежий dev
git switch -c feature/<задача>        # ветка под конкретную задачу
# ... коммиты, push, PR в dev, ревью, merge ...
git switch dev && git pull
git branch -d feature/<задача>        # удалить локальную ветку
git fetch --prune                     # подчистить remote-tracking ссылки
```

- Создавай ветку в момент начала задачи от свежего `dev`, а не заранее.
- Не переиспользуй уже смерженную ветку — заводи новую от `dev`.
- Включи на GitHub «Automatically delete head branches», чтобы remote-ветка
  удалялась автоматически при merge PR.
- Периодически чисти локальные влитые ветки: `git branch --merged dev`.

## Документация — в коде

Документов у проекта **намеренно мало**: они устаревали быстрее, чем правились,
и описывали классы, которых в коде никогда не существовало. Осталось три файла —
этот, [README.md](README.md) и [docs/data-format.md](docs/data-format.md).

Исключение для `docs/data-format.md` осознанное: он описывает не код, а **формат
данных на диске и контракт с прошивкой**. Это внешние обязательства — они меняются
редко, обдуманно и обеими сторонами сразу, поэтому не гниют так, как описание
классов. Ссылка на него уходит в `readme.txt` каждой папки эксперимента, то есть
к людям, которые репозиторий не открывали. Новые файлы в `docs/` заводить не
надо: подробности по данным дописываются в существующий.

Правила:

- **Объясняй рядом с кодом.** Всё, что можно сказать про класс, метод или порт, —
  в `///` над ним. Такой комментарий правится тем же движением, что и код, и не
  успевает разъехаться с ним.
- `///` пиши для тех, кто будет это читать: зачем нужен класс и какие у него
  неочевидные гарантии, а не пересказ сигнатуры. `// Увеличиваем счётчик` —
  мусор; «отсчёты за время разрыва не дописываются» — то, что нужно.
- **README — для того, кто пользуется программой.** Что это за проект, чем
  полезен, как поставить и с чего начать, куда идти за помощью. Внутренности,
  обоснования решений и порядок выпуска версии — сюда, в этот файл, а не в
  README.
- **`docs/data-format.md` — для того, кто получил данные.** Формат файлов и
  контракт с устройством. Поменял формат записи или контракт с прошивкой — правь
  его в том же PR, иначе человек на другом конце разберёт данные неправильно.
- **Один факт — в одном месте.** Не дублируй описание в README, в `docs/` и в
  `///`.
- Язык — русский; идентификаторы, имена файлов и команды — латиницей в `code`.
- Без хвостовых пробелов (проверяет CI).

## Стиль кода

Общий принцип: **новый код пишется в стиле окружающего**. Перед добавлением
посмотри соседние модули и следуй их структуре, именованию и форматированию.
Форматирование оставляем инструменту: следуем `dart format` и линтеру, не спорим
о пробелах и переносах вручную.

- всё сценарное состояние — в BLoC/Cubit; `setState` только для локальной
  визуальной мелочи, не для данных/записи/разметки/навигации;
- слои `presentation → application → domain`, `data → domain`, `platform → data`;
  UI не обращается напрямую к BLE и файловой системе;
- фичи изолированы, каждая со своими `presentation/application/domain/data`;
- внешние зависимости (BLE, файлы, часы) прячем за портами в `domain`, чтобы
  сценарии тестировались на фейках.

## Тесты

- Перед merge все тесты должны быть зелёными.
- Проверки запускаются из корня репозитория:

  ```bash
  flutter analyze
  flutter test
  dart format --set-exit-if-changed lib test
  ```

- Новый функционал сопровождается тестами; для важной логики покрываются и
  сбойные пути (ошибки, обрывы связи, граничные случаи).

## Коммиты

- Сообщение — на русском, англицизмы по минимуму (технические идентификаторы
  латиницей допустимы).
- Формат:

  ```text
  Краткий заголовок в повелительном наклонении

  - что изменено и зачем;
  - ещё один пункт при необходимости.
  ```

- Заголовок — до ~72 символов, без точки в конце.
- Один коммит — одно логическое изменение; не смешивай несвязанные правки.

## Pull request

- Базовая ветка — `dev`.
- В описании PR: **что** изменено, **зачем** и **как проверено** (какие тесты
  прогнаны или какая ручная проверка сделана).
- Чек-лист перед запросом ревью:
  - тесты зелёные;
  - `///` обновлены под изменение;
  - нет хвостовых пробелов;
  - если затронут контракт с прошивкой или откачено ключевое решение —
    поправлен [README.md](README.md).
- Ревью ведётся по сути и по контракту (помогает ли изменение текущему MVP,
  не ломает ли гарантии), а не по принципу «нравится / не нравится».

### Размер и ревью

- Держи PR **маленьким и сфокусированным** — одно логическое изменение. Маленький
  PR быстрее ревьюится, реже конфликтует и проще откатывается.
- Ревьюер смотрит: дизайн, корректность, сложность, тесты, именование,
  комментарии, документацию и стиль.
- Одобряем, когда изменение **улучшает общее состояние кода**, даже если оно не
  идеально. Необязательные придирки помечаем `nit:` и не блокируем ими merge.
- Ревью — приоритетная задача: на запрос ревью и на комментарии отвечаем быстро
  и по существу.

## Границы

Репозиторий — только приложение оператора. Веб-лаборатория и прошивка живут в
своих репозиториях; их код, инфраструктуру и доки сюда не тащим.

Сознательно **не делаем**: автоматический скоринг стадий сна по сигналу,
разметку и просмотр уже сохранённого эксперимента, выгрузку на сервер. Всё, что
за этой границей, обсуждаем до того, как писать код.
