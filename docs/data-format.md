# Формат данных эксперимента

Полное описание того, что приложение оператора записывает на диск, и того, как
это обрабатывать.

Документ рассчитан на человека, который получил папку с данными и должен их
разобрать. Приложение для этого не нужно и знание Flutter тоже: формат
самодостаточный, читается любым языком. Здесь намеренно продублировано всё, что
нужно для работы, включая словари меток, — чтобы не пришлось никого
расспрашивать.

Короткая выжимка того же самого лежит в `readme.txt` внутри каждой папки
эксперимента.

## Папка эксперимента

Оператор выбирает рабочую папку и вводит название эксперимента — папка с
данными называется так же:

```text
ФБМ_Группа1_Контроль/
  Мышь 1/
    signal.bin        сигнал после фильтров
    signal_raw.bin    сигнал как пришёл с устройства
    experiment.json   метаданные: фильтры, сегменты, разрывы, метки, ФБМ
    journal.ndjson    построчный журнал событий записи
    readme.txt        краткая памятка, генерируется при старте записи
```

Название папки — человеческое, его может изменить кто угодно. Машинный
идентификатор записи — `experiment_id` внутри `experiment.json`: это
[ULID](https://github.com/ulid/spec) (26 символов, лексикографически
сортируется по времени создания). Он связывает `journal.ndjson` с записью и
переживает переименование папки. Сопоставляя данные, опирайтесь на него, а не
на имя папки.

Ориентир по размеру: час записи — примерно 3,6 МБ на каждый `.bin`, то есть
~7,2 МБ на оба. Ночная запись на 12 часов — под 90 МБ.

## Сигнал

Оба `.bin` — подряд идущие отсчёты, без заголовка, без разделителей, без
выравнивания:

| | |
|---|---|
| тип отсчёта | `int32`, little-endian, 4 байта |
| единица | микровольты (мкВ) |
| частота дискретизации | 250 Гц (поле `recording.sample_rate_hz`) |
| число отсчётов | размер файла ÷ 4 |
| порядок | строго по времени, от начала записи |

Python:

```python
import numpy as np

x = np.fromfile('signal.bin', dtype='<i4')        # мкВ, после фильтров
raw = np.fromfile('signal_raw.bin', dtype='<i4')  # мкВ, без фильтров
t = np.arange(x.size) / 250                       # секунды от начала записи
```

MATLAB:

```matlab
f = fopen('signal.bin', 'r');
x = fread(f, inf, 'int32=>double', 'ieee-le');
fclose(f);
t = (0:numel(x)-1)' / 250;
```

R:

```r
n <- file.info("signal.bin")$size / 4
x <- readBin("signal.bin", "integer", n = n, size = 4, endian = "little")
```

Файлы всегда одной длины: отсчёт номер `N` в `signal.bin` и в `signal_raw.bin` —
один и тот же момент времени. Если длины разошлись, запись оборвалась
аварийно — берите минимум из двух.

### Почему файлов два

Фильтр необратим: убранное из сигнала не вернуть. Если фильтры при записи
выбрали неудачно — например, срезали то, что оказалось нужным, — из
`signal_raw.bin` можно перефильтровать заново, своими параметрами. В
`signal.bin` лежит то, что оператор видел на экране.

**Для спектрального анализа берите `signal_raw.bin`.** В `signal.bin` полосы за
границами фильтров уже подавлены, и мощность в них считать бессмысленно: вы
измерите характеристику фильтра, а не сигнал.

### Индекс отсчёта — это не время суток

`N / sample_rate_hz` даёт время **от начала записи по отсчётам**, а не реальное
время суток. Если связь с устройством обрывалась, отсчёты за время разрыва в
файл не попали, и настенное время «уехало» вперёд относительно индекса.

Нулями дырки не заполняются намеренно: синтетические отсчёты выглядели бы как
настоящий сигнал и испортили бы любой спектральный анализ. Разрывы описаны в
`gaps`, привязка к реальному времени — в полях `*_wall_clock`. Как правильно
восстановить время суток — в [разборе ниже](#восстановить-реальное-время-суток).

## Фильтры

Что применено к `signal.bin`, записано в `recording.filters`. Реализация —
Butterworth из библиотеки [iirjdart](https://pub.dev/packages/iirjdart),
фильтры **потоковые** (по одному отсчёту, вперёд по времени, без обратного
прохода), включены последовательно в таком порядке:

| фильтр | тип | порядок | параметры |
|---|---|---|---|
| `lp` | ФНЧ | 1 | частота среза из `hz` (по умолчанию 40 Гц) |
| `hp` | ФВЧ | 2 | частота среза из `hz` (по умолчанию 0,5 Гц) |
| `notch` | режекторный | 3 | центр из `hz` (по умолчанию 50 Гц), ширина полосы 10 Гц |

Важные следствия:

- Фильтрация **однопроходная**, поэтому вносит фазовый сдвиг. Если вам нужна
  точная привязка события ко времени, фильтруйте `signal_raw.bin` сами, с
  нулевой фазой (`scipy.signal.filtfilt`).
- Режекторный фильтр вырезает полосу **45–55 Гц** при настройке по умолчанию,
  а не одну частоту 50 Гц.
- В начале записи есть переходный процесс фильтра — первые доли секунды
  `signal.bin` не соответствуют сигналу. При анализе первую секунду разумно
  отбросить.
- По умолчанию включены все три фильтра. Проверяйте `enabled`: оператор мог их
  отключить.

## Откуда берутся отсчёты

Раздел нужен, только если вы разбираете поток с устройства напрямую, минуя
приложение. Формат общий с прошивкой в
[Test_eeg](https://github.com/duckduckduck1/Test_eeg) и меняется с обеих сторон
сразу.

**Транспорт.** Одна BLE-характеристика и на приём сигнала, и на управление:
`0000ffe1-0000-1000-8000-00805f9b34fb`.

**Поток.** 250 Гц, один отсчёт — три байта. Длина notify-payload кратна 3, но не
фиксирована (зависит от MTU): разбирать надо группами по 3 байта, а неполный
хвост буферизовать до следующего notify — иначе теряется выравнивание и весь
дальнейший сигнал превращается в шум.

**Декодирование.** Три байта складываются в 18-битное знаковое значение:

```text
adc = (b0 << 10) | (b1 << 2) | (b2 >> 6)     старшие 6 бит b2 не несут амплитуду
if adc >= 2^17: adc -= 2^18                  дополнительный код

eeg_uv = adc / 2^17 * (V_REF / GAIN) * 1e7   V_REF = 1.0 В, GAIN = 160
```

Для текущего стенда это ≈ `0.476837` мкВ на единицу АЦП. `V_REF` и `GAIN` —
параметры конкретного аналогового тракта: на другом железе множитель другой.

**Команда ФБМ** (свет) пишется в ту же характеристику, четыре байта:

```text
[on_off, pwm_byte, 0x0D, 0x0A]
```

`on_off` — `0x01` включить, `0x00` выключить. `pwm_byte` — яркость,
`round(pwm_level * 255 / 100)`. Завершающие `0x0D 0x0A` (CR LF) обязательны.

## experiment.json

Пишется атомарно (временный файл + переименование) при остановке записи и,
кроме того, примерно раз в полминуты во время неё. Кодировка UTF-8.

### Верхний уровень

| поле | тип | что это |
|---|---|---|
| `experiment_id` | строка | машинный ULID записи |
| `display_name` | строка | название эксперимента, им же названа папка |
| `metadata` | объект | произвольные пометки оператора, обычно пустой |
| `recording` | объект | параметры записи |
| `segments` | массив | непрерывные куски записи |
| `gaps` | массив | разрывы связи между сегментами |
| `labels` | массив | метки разметки |
| `fbm_sessions` | массив | сеансы света |

### recording

| поле | что это |
|---|---|
| `sample_rate_hz` | частота дискретизации, обычно 250 |
| `amplitude_unit` | всегда `microvolts` |
| `sample_encoding` | всегда `int32_le` |
| `filters` | что применено к `signal.bin`, см. [Фильтры](#фильтры) |
| `pwm_level` | заданная оператором яркость света, проценты (1–99) |

`amplitude_unit` и `sample_encoding` записаны явно, чтобы разбор не зависел от
договорённостей: читайте их, а не полагайтесь на то, что здесь написано.

### segments

Непрерывный кусок записи. Диапазон **полуоткрытый**: `[start_sample,
end_sample)` — отсчёт с индексом `end_sample` в сегмент уже не входит.

| поле | что это |
|---|---|
| `segment_id` | идентификатор сегмента |
| `start_sample`, `end_sample` | границы в индексах отсчётов |
| `start_time`, `end_time` | те же границы в `чч:мм:сс` от начала записи |
| `started_at_wall_clock`, `ended_at_wall_clock` | реальное время, UTC, ISO 8601 |

Первый сегмент всегда начинается с `start_sample: 0`. Границы сегментов
непрерывны по индексам: конец одного равен началу следующего, потому что
отсчётов за время разрыва в файле нет.

Незакрытый сегмент в `experiment.json` не попадает. В периодическом снимке
активный сегмент закрыт текущим счётчиком отсчётов — то есть выглядит
закрытым, хотя запись ещё шла.

### gaps

Разрыв связи между сегментами.

| поле | что это |
|---|---|
| `sample_index` | индекс отсчёта, на котором связь оборвалась |
| `time` | то же в `чч:мм:сс` |
| `started_at_wall_clock` | когда связь пропала, UTC |
| `ended_at_wall_clock` | когда восстановилась; **отсутствует**, если запись так и закончилась в разрыве |

Длительность разрыва считается **только** по `wall_clock`-полям: в отсчётах
разрыва нет по определению.

### labels

Метку ставит оператор глазами, по поведению животного, а не по сигналу.
Полный словарь — в разделе [Словарь меток](#словарь-меток).

Общие поля: `label_id`, `kind`, `label_type_id`, `segment_id`, `note`
(необязательное, свободный текст оператора).

Точечная метка (`kind: "event"`):

| поле | что это |
|---|---|
| `sample_index` | глобальный индекс отсчёта |
| `global_sample_index` | он же, явным именем (дубль для надёжности разбора) |
| `segment_sample_index` | индекс внутри своего сегмента |
| `time` | `чч:мм:сс` от начала записи |
| `wall_clock_time` | реальное время, UTC |

Интервальная метка (`kind: "state"` или `"exclude"`):

| поле | что это |
|---|---|
| `start_sample`, `end_sample` | глобальные границы, полуоткрытый диапазон |
| `start_segment_sample_index`, `end_segment_sample_index` | границы внутри сегмента |
| `start_time`, `end_time`, `duration` | то же в `чч:мм:сс` |
| `started_at_wall_clock`, `ended_at_wall_clock` | реальное время, UTC |

Метка всегда целиком лежит внутри одного сегмента: интервал через разрыв связи
невозможен. Незакрытые (черновые) метки в `experiment.json` не попадают — в
журнале они помечены `"draft": true`.

Интервалы одного вида могут пересекаться между собой: оператор ставит их
вручную, и приложение этого не запрещает. Если ваша обработка предполагает
непересекающиеся отрезки, проверяйте это сами.

### fbm_sessions

Один сеанс света — одна запись: включили, погасло. Сеанс не может выходить за
границы сегмента.

| поле | что это |
|---|---|
| `segment_id` | сегмент, в котором горел свет |
| `start_sample`, `end_sample` | границы в отсчётах |
| `start_time`, `end_time`, `duration` | то же в `чч:мм:сс` |
| `started_at_wall_clock`, `ended_at_wall_clock` | реальное время, UTC |
| `pwm_level` | яркость в процентах (1–99) |
| `pwm_byte` | что реально ушло в устройство: `round(pwm_level * 255 / 100)` |
| `start_command_delivered` | доехала ли до устройства команда «включить» |
| `end_reason` | почему погас |
| `end_command_delivered` | доехала ли команда «погасить» |
| `in_progress` | присутствует и равно `true`, если свет ещё горел на момент записи файла |

`end_reason` принимает значения:

| значение | что произошло |
|---|---|
| `manual` | оператор выключил сам |
| `auto_off_timer` | истекло заданное время |
| `connection_lost` | оборвалась связь |
| `recording_stopped` | остановили запись |

**Два поля, которые легко проглядеть.** `in_progress: true` означает, что перед
вами снимок, а не итог: `end_time` в нём — момент снимка, а не момент, когда
свет погас. А `end_command_delivered: false` (обычно вместе с
`end_reason: "connection_lost"`) означает, что команда «погасить» до устройства
не доехала и свет физически мог остаться включённым — фактическая засветка
дольше записанной. Такие сеансы при разборе стоит помечать отдельно, а не
считать наравне с остальными.

Симметрично, `start_command_delivered: false` означает, что свет мог и не
включиться, хотя сеанс записан.

## Словарь меток

Набор меток настраивается в приложении, поэтому единственный достоверный
источник для конкретной записи — `readme.txt` в её папке. Ниже — набор по
умолчанию, с которым собрано большинство записей.

Метки ставятся **по наблюдаемому поведению животного**, а не по сигналу.
Оператор — биолог, а не сомнолог: стадии сна по ЭЭГ он не размечает, это
задача постобработки. Не ищите в метках `sleep` соответствия NREM/REM — там его
нет, это «мышь спала, как это видно глазами».

### Состояния (`kind: "state"`) — интервалы

| `label_type_id` | название | цвет |
|---|---|---|
| `sleep` | Спит | `#9B7CFF` |
| `settling` | Пытается уснуть | `#6EA8FF` |
| `sitting` | Сидит | `#38BDF8` |
| `running` | Бегает | `#2EE6C8` |
| `exploring` | Исследует | `#22C55E` |
| `eating` | Ест | `#EAB308` |
| `drinking` | Пьёт | `#F59E0B` |
| `grooming` | Умывается | `#A855F7` |
| `nesting` | Роет / гнездо | `#94A3B8` |
| `freezing` | Замерла | `#F97316` |
| `agitated` | Беспокоится | `#FF5C6C` |
| `custom` | Своё состояние | `#CBD5E1` |

У `custom` смысл задаётся полем `note`: без него метка ничего не значит.

### События (`kind: "event"`) — точки

| `label_type_id` | название | цвет |
|---|---|---|
| `woke_up` | Проснулась | `#FACC15` |
| `startle` | Вздрогнула | `#FB7185` |
| `twitch` | Дёрнулась | `#38BDF8` |
| `external_noise` | Внешний шум | `#F59E0B` |
| `cage_touched` | Трогали клетку | `#C084FC` |
| `custom_event` | Своя отметка | `#CBD5E1` |
| `wire_touched` | Задели провод | `#F43F5E` |
| `sensor_hit` | Ударилась датчиком | `#FB7185` |
| `electrode_moved` | Сместился электрод | `#E879F9` |
| `interference` | Наводка / помеха | `#FDBA74` |

Последние четыре — **технические**: они объясняют, откуда на записи скачок
амплитуды. Если рядом с артефактом на сигнале стоит `wire_touched` или
`electrode_moved`, это не физиология, а механика, и такой участок разумно
исключить, даже если оператор не поставил `artifact`.

### Исключения (`kind: "exclude"`) — интервалы

| `label_type_id` | название | цвет |
|---|---|---|
| `artifact` | Артефакт сигнала | `#F43F5E` |

Участок, который оператор считает непригодным для анализа. Это рекомендация
человека, смотревшего на сигнал вживую, — обычно ей стоит доверять.

## journal.ndjson

Append-only журнал: по одному JSON-объекту в строке, в порядке событий,
кодировка UTF-8. Пишется по ходу записи, поэтому переживает то, чего
`experiment.json` может не пережить.

У каждой строки есть `type`, `experiment_id` и `timestamp` (UTC, ISO 8601);
у большинства — `segment_id` и `sample_index`.

```json
{"type":"experiment_started","experiment_id":"01J8ZC…","timestamp":"2026-07-19T21:00:00.000Z"}
{"type":"segment_started","experiment_id":"01J8ZC…","timestamp":"2026-07-19T21:00:00.000Z","segment_id":"seg-1","sample_index":0}
{"type":"connection_lost","experiment_id":"01J8ZC…","timestamp":"2026-07-19T21:30:00.000Z","segment_id":"seg-1","sample_index":450000}
```

| `type` | когда пишется |
|---|---|
| `experiment_started` | старт записи |
| `segment_started` | открыт новый сегмент |
| `segment_ended` | сегмент закрыт |
| `connection_lost` | оборвалась связь |
| `connection_resumed` | связь восстановилась |
| `annotation_created` | оператор поставил метку |
| `annotation_updated` | метка изменена (например, закрыт интервал) |
| `annotation_deleted` | метка удалена |
| `fbm_event` | включение или выключение света |
| `recording_stopped` | запись остановлена |

Журнал — запасной путь восстановления. Если `experiment.json` оказался старше
данных (приложение упало, выключилось питание), полную картину можно собрать
отсюда: границы сегментов, разрывы, метки и ФБМ записаны по порядку.

Обратите внимание: метка, созданная и потом удалённая, в журнале остаётся —
там есть и `annotation_created`, и `annotation_deleted`. В `experiment.json` её
уже нет. Если разбираете журнал, применяйте события по порядку, а не считайте
все `annotation_created` действующими метками.

## Разбор: типовые задачи

Всюду ниже:

```python
import json
import numpy as np

meta = json.load(open('experiment.json', encoding='utf-8'))
fs = meta['recording']['sample_rate_hz']
x = np.fromfile('signal.bin', dtype='<i4')
raw = np.fromfile('signal_raw.bin', dtype='<i4')
```

### Нарезать сигнал по сегментам

```python
for seg in meta['segments']:
    chunk = x[seg['start_sample']:seg['end_sample']]   # диапазон полуоткрытый
    print(seg['segment_id'], chunk.size / fs, 'с')
```

### Восстановить реальное время суток

Индекс отсчёта считает только записанные отсчёты, поэтому переводить его в
время суток можно **только внутри сегмента**, от начала этого сегмента:

```python
from datetime import datetime, timedelta

def wall_clock(sample_index):
    for seg in meta['segments']:
        if seg['start_sample'] <= sample_index < seg['end_sample']:
            t0 = datetime.fromisoformat(
                seg['started_at_wall_clock'].replace('Z', '+00:00')
            )
            offset = (sample_index - seg['start_sample']) / fs
            return t0 + timedelta(seconds=offset)
    raise ValueError(f'отсчёт {sample_index} не попал ни в один сегмент')
```

Наивное `начало_записи + N / fs` даст ошибку, равную суммарной длительности всех
разрывов до этой точки.

### Вырезать участки, помеченные как артефакты

```python
mask = np.ones(x.size, dtype=bool)
for label in meta['labels']:
    if label['kind'] == 'exclude':
        mask[label['start_sample']:label['end_sample']] = False

clean = x[mask]
```

`clean` уже не соответствует исходным индексам. Если индексы нужны дальше,
работайте с маской, а не с урезанным массивом.

Строже — исключить и окрестности технических событий:

```python
technical = {'wire_touched', 'sensor_hit', 'electrode_moved', 'interference'}
guard = int(2 * fs)                      # ±2 секунды вокруг события

for label in meta['labels']:
    if label['label_type_id'] in technical:
        i = label['sample_index']
        mask[max(0, i - guard):min(x.size, i + guard)] = False
```

### Собрать интервалы одного состояния

```python
sleeping = [
    (lb['start_sample'], lb['end_sample'])
    for lb in meta['labels']
    if lb['kind'] == 'state' and lb['label_type_id'] == 'sleep'
]

total_sleep_s = sum(b - a for a, b in sleeping) / fs
```

### Отделить сигнал под светом от сигнала без света

```python
under_light = np.zeros(x.size, dtype=bool)
suspect = []

for s in meta['fbm_sessions']:
    if s.get('in_progress'):
        continue                                  # не итог, а снимок
    under_light[s['start_sample']:s['end_sample']] = True
    if not s.get('end_command_delivered', True):
        suspect.append(s)                         # свет мог гореть дольше

light = x[under_light]
dark = x[~under_light]
```

`suspect` стоит просмотреть глазами: в этих сеансах граница «свет погас»
недостоверна.

### Посчитать спектр честно

Берём сырой сигнал, вырезаем артефакты, считаем по сегментам — склеивать куски
через разрыв нельзя, на стыке возникнет скачок:

```python
from scipy import signal as sp

for seg in meta['segments']:
    chunk = raw[seg['start_sample']:seg['end_sample']].astype(float)
    f, pxx = sp.welch(chunk, fs=fs, nperseg=int(4 * fs))
```

## Ритмы, как их считало приложение

Если нужно воспроизвести то, что оператор видел на экране: приложение считает
мощность по полосам через FFT по окну в **1024 отсчёта** (≈4,1 с при 250 Гц) с
**окном Ханна**, пересчёт — **раз в секунду**. Границы полос (Гц, диапазоны
полуоткрытые):

| ритм | полоса |
|---|---|
| Delta | 0,5–4 |
| Theta | 4–8 |
| Alpha | 8–13 |
| Beta | 13–35 |

Эти значения — то, что показывалось на графике живого сигнала. **В файлы ритмы
не записываются:** на диск идёт сигнал, а не производные от него, иначе они
разъехались бы с ним при любой перефильтровке. Считать ритмы заново вы вольны
как угодно — приведённые параметры даны для сопоставления с тем, что видел
человек за прибором.

Учтите, что на графике ритмы считались от **отфильтрованного** сигнала, поэтому
Beta выше 40 Гц там подавлена ФНЧ, а всё вокруг 50 Гц вырезано режекторным
фильтром.

## На что обратить внимание

- **Индекс отсчёта ≠ время суток.** При разрывах связи они расходятся; для
  реального времени есть `*_wall_clock` и рецепт
  [выше](#восстановить-реальное-время-суток).
- **Диапазоны полуоткрытые** — `[начало, конец)`. Прибавлять единицу к `end` не
  нужно.
- **`in_progress: true`** — снимок, а не итог.
- **`end_command_delivered: false`** — свет мог остаться включённым, хотя сеанс
  в файле закрыт.
- **`signal.bin` отфильтрован** однопроходным фильтром: есть фазовый сдвиг и
  переходный процесс в начале. Для спектра и точной привязки событий берите
  `signal_raw.bin`.
- **Метки могут пересекаться** — приложение этого не запрещает.
- **Словарь меток может отличаться** от приведённого здесь: сверяйтесь с
  `readme.txt` конкретной папки.

## Частые вопросы

**Мне нужен только один файл — какой?** `signal_raw.bin` плюс
`experiment.json`. Первый — данные, второй — всё, что нужно, чтобы понять, что
это за данные.

**Почему в сигнале скачок на несколько тысяч мкВ?** Почти наверняка механика:
посмотрите метки рядом по времени — `wire_touched`, `sensor_hit`,
`electrode_moved`. Физиологический сигнал таких амплитуд не даёт.

**Длина `.bin` не делится на 4 нацело.** Запись оборвалась на середине отсчёта
(выключилось питание). Отбросьте хвост: `x = x[:len(x) // 4 * 4]` на уровне
байт.

**`experiment.json` не читается или обрывается.** Он пишется атомарно, поэтому
такого быть не должно; если случилось — собирайте картину из `journal.ndjson`,
там всё то же самое, только по событиям.

**В `segments` пусто, а сигнал есть.** Запись оборвалась до первого сохранения
метаданных. Границы сегментов ищите в `journal.ndjson` по `segment_started` и
`segment_ended`.

**Сколько длилась запись?** По отсчётам — `len(x) / fs`. По часам — разница
между `started_at_wall_clock` первого сегмента и `ended_at_wall_clock`
последнего; она будет больше на суммарную длительность разрывов.

**Можно ли доверять `display_name`?** Как названию — да, его вводил оператор.
Как идентификатору — нет, папку могли переименовать. Идентификатор —
`experiment_id`.
