# Архитектура приложения

Как устроен код приложения оператора: структура `lib/`, слои, направление
зависимостей и распределение состояния по BLoC/Cubit. Документ описывает
текущее состояние кода.

## Структура `lib/`

```text
lib/
  main.dart          точка входа: verbose-логи BLE в debug, runApp
  main_app.dart      корневой виджет: тема, зависимости, глобальные Cubit
  theme.dart         единая тёмная тема «Осциллограф» (cyan-акцент, Material 3)
  core/              общее: типы ошибок, модель отсчёта сигнала
  features/          доменные фичи (devices, recording, annotation, navigation)
  fuetures/          экраны и виджеты (ble_page, main_layout, main_page)
  platform/          платформенные адаптеры (ble/flutter_blue_plus_adapter.dart)
```

> `fuetures/` — опечатка в имени каталога, доставшаяся от прототипа. Каталог
> живой; переименование затронет все импорты и пока не сделано.

## Слои и зависимости

Внутри фичи зависимости идут строго в одну сторону:

```text
presentation → application → domain
data         → domain
platform     → data/domain
```

- `domain` — модели и **порты** (абстрактные интерфейсы); не знает ни про
  Flutter, ни про плагины, ни про файловую систему.
- `data` — реализации портов поверх реального мира: файлы, декодер, фильтры.
- `application` — сценарии: BLoC/Cubit и мосты между потоками данных.
- `presentation` — виджеты и диалоги; UI не обращается к BLE и файлам напрямую.

Порты — это то, что делает сценарии тестируемыми без железа: в тестах вместо
реализации подставляется фейк (см. [testing.md](testing.md)).

## Фичи

| Фича | Что внутри |
|------|------------|
| `features/devices` | порты BLE (`BleAdapter`, `BleConnection`), декодер отсчётов, поиск, подключение, сессии устройств |
| `features/recording` | запись эксперимента: модели, порты, `RecordingBloc`, файловое хранилище, потоковые фильтры, транспорт ФБМ |
| `features/annotation` | модели меток, справочник типов, окно разметки |
| `features/navigation` | `NavigationCubit` — переходы между экранами |

Логика разметки живёт **в `RecordingBloc`**, а не в отдельном bloc: метка
привязана к текущему сегменту и счётчику отсчётов записи, поэтому источник
«сейчас» — состояние записи. В `features/annotation` остались только модели,
справочник и UI.

## Состояние

Всё сценарное состояние — в BLoC/Cubit. `setState` допустим только для локальной
визуальной мелочи, не для данных, записи, разметки и навигации.

| Кто | Область |
|-----|---------|
| `SessionsCubit` | сессии подключённых устройств (глобально) |
| `NavigationCubit` | текущий экран, намерение открыть вкладку устройства |
| `DeviceDiscoveryBloc` | поиск устройств |
| `DeviceConnectionBloc` | подключение, ручное переподключение, активное соединение |
| `TabBloc` | вкладки и их `RecordingBloc` / `DeviceConnectionBloc` |
| `RtEegDataBloc` | живые данные графиков: сигнал, спектр, ритмы |
| `RecordingBloc` | запись, сегменты, разрывы, ФБМ, метки |

На каждое устройство — свой набор экземпляров: вкладка владеет собственными
`RtEegDataBloc` и `RecordingBloc`, поэтому устройства не мешают друг другу.

## Точка входа и зависимости

`MainApp` поднимает провайдеры реализаций и глобальные Cubit:

```text
RepositoryProvider<BleAdapter>           → FlutterBluePlusAdapter
RepositoryProvider<RecordingBlocFactory> → FileRecordingBlocFactory
BlocProvider<SessionsCubit>
BlocProvider<NavigationCubit>
```

Зависимости приходят через провайдеры, а не через глобальные singleton.
`RecordingBlocFactory` — тоже порт: в приложении создаёт `RecordingBloc` поверх
файлового хранилища, в тестах подменяется фейком.

## Мосты

Поток данных с устройства расходится к двум потребителям через мосты в
`application`:

- `DeviceEegBridge` — пакеты BLE → `RtEegDataBloc` (живые графики);
- `RecordingBridge` — пакеты BLE → `RecordingBloc` (запись), плюс события
  обрыва и восстановления связи.

Оба живут на вкладке устройства и завершаются вместе с ней.

## Настройки

Настройки живут в рамках сессии и на диск не сохраняются:

- панель видимости графиков (сигнал, спектр, ритмы);
- фильтры отображения (LP, HP, Notch) — влияют на картинку, но не на запись;
- фильтры записи и уровень ШИМ задаются в диалоге старта эксперимента и
  фиксируются в `experiment.json`.
