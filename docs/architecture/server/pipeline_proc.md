# pipeline_proc.md

## Пайплайн обработки

Пайплайн обработки — серверный блок, который запускается после успешной валидации
и принятия эксперимента. Он читает исходный пакет эксперимента из хранилища,
выполняет расчёты и сохраняет производные результаты.

Пайплайн не изменяет исходные файлы эксперимента. `signal.bin` и
`experiment.json` остаются первичными данными.

---

## Сквозные принципы

1. **Пайплайн запускается только для валидных экспериментов.** Эксперимент должен
   иметь статус `accepted`.

2. **Обработка создаёт производные данные.** Исходный пакет не переписывается.

3. **Запуск должен быть повторяемым.** Повторная обработка одного эксперимента не
   должна ломать исходные данные.

4. **Первичный запуск выполняется автоматически.** После успешной валидации и
   принятия эксперимента сервер сам запускает пайплайн обработки.

5. **Повторный запуск выполняется вручную.** Если обработку нужно повторить,
   пользователь или администратор явно инициирует повторный запуск.

6. **Ошибки обработки фиксируются.** Пользователь должен видеть причину сбоя, а
   не только общий статус ошибки.

7. **Пайплайн работает в изолированной среде.** На схеме это Docker-контейнеры.
   Конкретная реализация фиксируется позже.

---

## 1. Вход пайплайна

Пайплайн получает:

- ссылку на принятый эксперимент;
- `signal.bin`;
- `experiment.json`;
- метаданные эксперимента;
- информацию о сегментах и разрывах;
- разметку, если она есть;
- параметры обработки.

Пайплайн не должен получать эксперимент напрямую от Flutter-приложения. Входом
является только эксперимент, уже принятый сервером и сохранённый в хранилище.

---

## 2. Основные функции

2.1. Загрузка исходных данных из хранилища.

2.2. Проверка, что эксперимент имеет статус `accepted`.

2.3. Запуск обработки в Docker-контейнере или наборе контейнеров.

2.4. Расчёт производных данных.

2.5. Сохранение результатов обработки в хранилище.

2.6. Обновление статуса эксперимента в PostgreSQL.

2.7. Сохранение логов обработки.

2.8. Возврат ошибок обработки в серверный слой статусов.

2.9. Первичный запуск пайплайна выполняется автоматически после перехода
     эксперимента в статус `accepted`.

---

## 3. Возможные результаты обработки

На текущем архитектурном этапе результаты описываются обобщённо:

- обработанные версии сигнала;
- спектральные признаки;
- таблицы расчётов;
- графики;
- отчёты;
- служебные логи обработки;
- архив результатов.

Конкретный состав результатов фиксируется позже, когда будет описываться
реализация обработки данных.

---

## 4. Статусы обработки

Пайплайн работает со статусами:

- `processing` — обработка запущена;
- `processed` — обработка завершена успешно;
- `processing_failed` — обработка завершилась ошибкой.

При ошибке нужно сохранить:

- на каком этапе произошёл сбой;
- краткую причину;
- технический лог;
- возможность повторного запуска после исправления причины.

---

## 5. Хранение результатов

Результаты пайплайна сохраняются отдельно от исходных данных:

- файлы результатов — в файловом хранилище;
- ссылки на результаты — в PostgreSQL;
- статус обработки — в PostgreSQL;
- логи обработки — в файловом хранилище или в системе логирования.

Веб-интерфейс должен читать результаты через сервер, а не напрямую из контейнера
пайплайна.

---

## 6. Повторный запуск

Повторный запуск обработки нужен, если:

- предыдущий запуск завершился ошибкой;
- изменились параметры обработки;
- появилась новая версия пайплайна;
- нужно пересчитать производные результаты.

Повторный запуск не выполняется автоматически. Его инициирует пользователь или
администратор через серверный интерфейс, когда причина для пересчёта понятна.

Повторный запуск не должен менять исходный пакет эксперимента. Новые результаты
должны либо заменять старые производные результаты по явному правилу, либо
сохраняться как новая версия результата. Это решение фиксируется позже на этапе
реализации.

---

## 7. Что не входит в этот блок

- приём файлов от приложения;
- валидация структуры эксперимента;
- хранение исходного пакета как задача приёма;
- веб-просмотр;
- ручная разметка;
- автоматическое определение фаз сна;
- ML/MLOps на текущем этапе.
