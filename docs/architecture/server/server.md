# server.md

## Сервер

Сервер — центральный узел второго звена системы. Он принимает готовые
эксперименты через веб-интерфейс, запускает проверку, сохраняет принятые данные,
передаёт эксперименты в пайплайн обработки и отдаёт статусы через серверный UI и
API.

Сервер не участвует в live-записи ЭЭГ и не управляет устройством. Запись должна
быть полностью работоспособной даже при недоступном сервере.

---

## Сквозные принципы

1. **Сервер не находится в критическом пути записи.** Потеря сети или падение
   сервера не должны мешать локальному сбору данных.

2. **Сервер принимает только завершённые локальные эксперименты.** Единица
   передачи — папка или архив эксперимента, выбранные пользователем вручную в
   Web UI.

3. **Перед загрузкой пользователь аутентифицируется в Web UI.** Сервер не
   принимает эксперименты от неизвестных пользователей. Прямая загрузка из
   Flutter-приложения не входит в MVP.

4. **Сервер не исправляет данные молча.** Если эксперимент некорректен, сервер
   возвращает понятную ошибку валидации.

5. **Исходный пакет эксперимента неизменяем.** Обработка создаёт производные
   результаты, но не переписывает `signal.bin` и `experiment.json`.

6. **Все этапы имеют статус.** Пользователь должен видеть, где находится
   эксперимент: загрузка, проверка, принятие, обработка, ошибка.

---

## 1. Основные функции

1.1. Приём ручной загрузки экспериментов через Web UI.

1.2. Аутентификация web-пользователя перед созданием загрузочной сессии.

1.3. Создание загрузочной сессии для конкретного `experiment_id`.

1.4. Проверка, не был ли эксперимент с таким `experiment_id` уже принят ранее.

1.5. Приём файлов пакета эксперимента.

1.6. Передача принятого пакета в блок валидации.

1.7. Сохранение статусов загрузки, валидации и обработки.

1.8. Передача валидных экспериментов в хранилище данных.

1.9. Запуск пайплайна обработки после успешной валидации.

1.10. Возврат статусов и ошибок в Web UI.

1.11. Предоставление данных для веб-интерфейса.

---

## 2. Входящие данные

Сервер получает через Web UI пакет эксперимента, созданный Flutter-приложением:

- `signal.bin` — бинарный сигнал, int32, значения амплитуды в мкВ;
- `experiment.json` — описание эксперимента;
- `journal.ndjson` — append-only журнал событий, если отправляется;
- `app.log` — технический лог приложения, если отправляется.

Физический формат передачи фиксируется позже на этапе реализации. Это может быть
архив, multipart upload или другой механизм. На архитектурном уровне важно, что
сервер получает самодостаточный пакет эксперимента.

---

## 3. Загрузочная сессия

3.1. Перед началом загрузки пользователь аутентифицируется в Web UI.

3.2. Web UI запрашивает создание загрузочной сессии для `experiment_id`.

3.3. Сервер проверяет, не существует ли уже принятого эксперимента с таким
     `experiment_id`.

3.4. Если эксперимент уже принят, сервер не создаёт дубль автоматически.

3.5. Если предыдущая загрузка была неполной, сервер может разрешить повторную
     загрузку или перезапуск загрузочной сессии.

3.6. В рамках одной загрузочной сессии сервер принимает файлы одного
     эксперимента.

---

## 4. Статусы

Сервер ведёт статусы эксперимента:

- `uploading` — файлы загружаются;
- `uploaded` — загрузка завершена;
- `validating` — идёт проверка структуры и целостности;
- `accepted` — эксперимент прошёл проверку и принят;
- `validation_failed` — эксперимент не прошёл проверку;
- `processing` — запущена обработка;
- `processed` — обработка завершена;
- `processing_failed` — обработка завершилась ошибкой.

Статусы должны быть доступны веб-интерфейсу. Приложение может получить прямую
синхронизацию статусов позже, но MVP не зависит от этого.

---

## 5. Ответы Web UI

Сервер возвращает веб-интерфейсу:

- успешное создание загрузочной сессии;
- отказ в создании сессии с причиной;
- прогресс или итог загрузки;
- результат валидации;
- ошибки валидации с понятным описанием;
- статус обработки;
- информацию о том, что эксперимент уже принят сервером.

Ошибки должны быть прикладными, а не только техническими. Например:

- нет `experiment.json`;
- нет `signal.bin`;
- сегмент выходит за пределы бинарника;
- метка ссылается на несуществующий сегмент;
- эксперимент уже принят;
- файл повреждён.

---

## 6. Мониторинг и эксплуатация

Сервер должен быть наблюдаемым:

- состояние сервиса;
- количество загрузок;
- ошибки загрузок;
- ошибки валидации;
- ошибки пайплайна;
- состояние очереди обработки;
- доступность базы данных;
- состояние бэкапов;
- алерты по критическим сбоям.

Инструменты мониторинга: Prometheus, Grafana, алерты и разбор инцидентов.
Конкретная реализация фиксируется позже.

---

## 7. Что не входит в серверный блок

- live-streaming сигнала;
- управление BLE-устройством;
- управление фотобиомодуляцией;
- локальное восстановление записи после краша приложения;
- ручная разметка;
- автоматическое определение фаз сна;
- ML/MLOps.
