# server.md

## Взаимодействие приложения с сервером

Сервер используется для приёма, проверки, хранения и последующей обработки
готовых экспериментов. Он не участвует в live-записи и не является частью
критического пути сбора данных с устройства.

Flutter-приложение сначала надёжно записывает эксперимент локально: принимает
сигнал по BLE, пишет бинарник, ведёт журнал событий, собирает JSON-описание и
сохраняет папку эксперимента на компьютере экспериментатора. Только после этого
пользователь вручную выбирает один или несколько экспериментов и отправляет их на
сервер.

---

## Сквозные принципы

1. **Запись не зависит от сервера.** Если сервер недоступен или сеть отключена,
   локальная запись эксперимента продолжается без потери данных.

2. **Отправка на сервер выполняется вручную.** Приложение не загружает
   эксперимент автоматически после завершения записи. Пользователь сам выбирает
   папку или несколько папок экспериментов для отправки.

3. **Сервер принимает данные только от авторизованного приложения.** Перед
   созданием загрузочной сессии приложение аутентифицируется на сервере. Способ
   аутентификации фиксируется позже на этапе реализации.

4. **Папка эксперимента — единица передачи.** Каждый эксперимент хранится в
   отдельной папке с пользовательским названием. Внутри папки лежат все файлы,
   необходимые для переноса и последующей обработки.

5. **Исходные данные сохраняются неизменными.** Сервер может запускать обработку
   и создавать производные результаты, но исходный пакет эксперимента не
   перезаписывается.

6. **Повторная отправка должна быть безопасной.** Если загрузка оборвалась,
   пользователь может запустить её повторно. Сервер не должен молча создавать
   дубликаты одного и того же эксперимента.

7. **Локальная копия не удаляется автоматически.** После успешной отправки папка
   эксперимента остаётся на компьютере экспериментатора. Удаление или
   архивирование выполняется только вручную.

---

## 1. Граница ответственности

### 1.1. Flutter-приложение отвечает за:

- сбор сигнала с устройства по BLE;
- локальную запись `signal.bin`;
- ведение append-only журнала событий во время записи;
- сборку финального `experiment.json`;
- локальное восстановление после сбоя приложения или системы;
- ручную разметку;
- хранение папки эксперимента на компьютере экспериментатора;
- аутентификацию на сервере перед отправкой;
- ручную отправку выбранных папок экспериментов на сервер.

### 1.2. Сервер отвечает за:

- приём готовых экспериментов от приложения;
- проверку структуры и целостности файлов;
- хранение исходных пакетов экспериментов;
- хранение карточек экспериментов и статусов в базе данных;
- запуск обработки после успешной проверки;
- хранение результатов обработки;
- предоставление доступа к экспериментам и результатам через веб-интерфейс;
- бэкапы, мониторинг и эксплуатационную надёжность.

### 1.3. Сервер не отвечает за:

- BLE-подключение к устройству;
- live-запись сигнала;
- управление фотобиомодуляцией;
- восстановление локальной записи после краша;
- автоматическую разметку;
- автоматическое определение фаз сна;
- ML-классификацию состояний.

---

## 2. Папка эксперимента

При создании эксперимента пользователь задаёт человекочитаемое название
эксперимента. По этому названию приложение создаёт отдельную папку, например
`exp1`.

Пример структуры:

```text
experiments/
  exp1/
    signal.bin
    experiment.json
    journal.ndjson
    app.log
```

Название папки нужно для удобства пользователя. Внутри `experiment.json` должен
быть технический уникальный `experiment_id`, созданный приложением. Сервер
ориентируется именно на `experiment_id`, а не только на имя папки.

Это нужно, чтобы:

- разные эксперименты могли иметь похожие пользовательские названия;
- переименование папки не ломало идентификацию эксперимента;
- повторная отправка не создавала дубликат без явного решения пользователя.

---

## 3. Состав пакета эксперимента

Минимальный пакет эксперимента:

- `signal.bin` — бинарный сигнал, int32, обработанные значения амплитуды в мкВ;
- `experiment.json` — метаданные, параметры записи, сегменты, разрывы,
  разметка, события ФБМ и ссылки на отсчёты в бинарнике.

Дополнительные файлы:

- `journal.ndjson` — append-only журнал событий, из которого собирался финальный
  JSON;
- `app.log` — технический лог приложения для диагностики проблем записи,
  подключения и отправки.

`journal.ndjson` и `app.log` полезны для диагностики, но основным контрактом с
сервером остаются `signal.bin` и `experiment.json`.

---

## 4. Ручная отправка на сервер

4.1. Пользователь завершает запись эксперимента локально.

4.2. Приложение собирает финальный `experiment.json` из append-only журнала.

4.3. Эксперимент остаётся на компьютере экспериментатора как папка с файлами.

4.4. Пользователь открывает раздел отправки на сервер.

4.5. Приложение аутентифицируется на сервере перед созданием загрузочной сессии.

4.6. Пользователь выбирает одну папку эксперимента или несколько папок
     экспериментов.

4.7. Приложение перед отправкой проверяет выбранные папки:
     - есть ли обязательные файлы;
     - читается ли `experiment.json`;
     - существует ли `signal.bin`;
     - согласованы ли базовые ссылки JSON с размером бинарника.

4.8. Приложение отправляет каждый выбранный эксперимент как отдельный пакет.

4.9. Ошибка отправки одного эксперимента не должна останавливать отправку
     остальных выбранных экспериментов.

4.10. Пользователь видит статус отправки по каждому эксперименту отдельно:
      не отправлен, отправляется, ошибка отправки, загружен, принят сервером.

---

## 5. Жизненный цикл загрузки

1. Приложение аутентифицируется на сервере.

2. Приложение создаёт на сервере сессию загрузки для конкретного
   `experiment_id`.

3. Сервер проверяет, нет ли уже принятого эксперимента с таким `experiment_id`.

4. Приложение загружает файлы пакета эксперимента.

5. Сервер проверяет целостность и структуру загруженных файлов.

6. Если проверка успешна, сервер принимает эксперимент и переводит его в статус
   `accepted`.

7. Если проверка неуспешна, сервер возвращает ошибку с понятной причиной.

8. После принятия сервер может запустить обработку эксперимента.

9. Приложение показывает пользователю итоговый статус загрузки.

Физический способ передачи файлов фиксируется позже на этапе реализации. Это
может быть архив, multipart upload или другой механизм. На уровне архитектуры
важно, что сервер принимает самодостаточный пакет эксперимента.

---

## 6. Проверка на сервере

Минимальные проверки при приёме:

- пакет содержит `signal.bin`;
- пакет содержит `experiment.json`;
- `experiment.json` читается и соответствует ожидаемой структуре;
- размер `signal.bin` соответствует последовательности int32;
- сегменты не выходят за пределы бинарника;
- разрывы ссылаются на существующие соседние сегменты;
- разметка ссылается на существующие сегменты и отсчёты;
- интервальные метки не пересекают границы сегментов;
- события ФБМ ссылаются на существующие сегменты и отсчёты;
- sample rate в описании соответствует параметрам записи;
- `experiment_id` присутствует и валиден.

Сервер не должен молча исправлять исходный эксперимент. Если данные некорректны,
он возвращает ошибку валидации. Исправление выполняется на стороне приложения или
пользователем после анализа причины.

---

## 7. Статусы эксперимента на сервере

Возможные статусы:

- `uploading` — файлы загружаются;
- `uploaded` — загрузка завершена, проверка ещё не закончена;
- `validating` — сервер проверяет структуру и целостность;
- `accepted` — эксперимент принят сервером;
- `validation_failed` — эксперимент не прошёл проверку;
- `processing` — запущена обработка;
- `processed` — обработка завершена;
- `processing_failed` — обработка завершилась ошибкой.

Статус должен быть виден пользователю, чтобы было понятно, что произошло с
каждым отправленным экспериментом.

---

## 8. Повторная отправка и ошибки

8.1. Если сеть оборвалась во время отправки, локальная папка эксперимента не
     изменяется.

8.2. Пользователь может повторить отправку выбранного эксперимента.

8.3. Сервер определяет эксперимент по `experiment_id`.

8.4. Если эксперимент с таким `experiment_id` уже принят, сервер не создаёт
     дубликат автоматически.

8.5. Если предыдущая загрузка была неполной, сервер может разрешить повторную
     загрузку или перезапуск загрузочной сессии.

8.6. Ошибки должны быть понятными: не просто "upload failed", а причина уровня
     "нет experiment.json", "сегмент выходит за пределы signal.bin", "файл
     повреждён", "эксперимент уже принят".

---

## 9. Локальная папка после отправки

9.1. После успешной отправки и принятия сервером локальная папка эксперимента не
     удаляется автоматически.

9.2. Локальная папка остаётся рабочей копией на компьютере экспериментатора.

9.3. Приложение может показывать, что эксперимент уже принят сервером, но это не
     означает автоматическое удаление локальных файлов.

9.4. Удаление или архивирование локального эксперимента выполняется только
     вручную пользователем.

9.5. Удаление локальной папки допустимо только после явного подтверждения
     пользователя и только если эксперимент уже успешно принят сервером.

---

## 10. Хранение на сервере

Сервер хранит два типа данных:

1. **Исходный пакет эксперимента.** Файлы, пришедшие от приложения:
   `signal.bin`, `experiment.json`, при необходимости `journal.ndjson` и
   `app.log`.

2. **Служебные и производные данные.** Записи в PostgreSQL, статусы загрузки,
   результаты обработки, ссылки на файлы, данные для веб-интерфейса.

Исходный пакет эксперимента должен оставаться неизменным. Любая обработка создаёт
новые производные результаты, а не переписывает первичные данные.

---

## 11. Что не входит в этот этап

- live-streaming сигнала на сервер;
- управление устройством с сервера;
- управление ФБМ с сервера;
- автоматическая отправка после завершения записи;
- автоматическая разметка;
- автоматическое определение фаз сна;
- ML/MLOps;
- Kubernetes и Terraform;
- сложная ролевая модель пользователей.
