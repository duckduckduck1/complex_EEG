# runbook.md

## Runbook

Runbook — эксплуатационная инструкция для типовых ситуаций. Он нужен, чтобы при
сбое не вспоминать архитектуру с нуля, а быстро понять: что проверить, где
посмотреть статус, какие действия безопасны, когда нужен бэкап и когда нельзя
трогать данные.

Этот документ описывает сценарии на уровне действий и ответственности. Конкретные
команды будут добавляться позже, когда появится реализация.

---

## Сквозные принципы

1. **Сначала диагностика, потом действие.** Не перезапускать всё подряд, пока не
   понятно, какой слой сломался.

2. **Данные не удалять без явного решения.** Эксперименты, PostgreSQL volume,
   бэкапы и результаты обработки нельзя чистить как временные файлы.

3. **Перед рискованными действиями нужен бэкап.** Особенно перед миграциями БД,
   массовым удалением, восстановлением или обновлением.

4. **Каждый инцидент должен оставлять след.** Нужно понимать причину, действие и
   результат.

---

## 1. Проверка здоровья системы

Базовая проверка:

- сервер доступен по SSH;
- Docker работает;
- контейнеры запущены;
- API отвечает;
- web отвечает;
- PostgreSQL доступен;
- диск не заполнен;
- последние бэкапы успешны;
- Prometheus собирает метрики;
- Grafana открывается;
- пайплайн не застрял.

Эта проверка нужна после перезагрузки, обновления и при жалобах пользователей.

---

## 2. Сервер недоступен

Проверить:

- доступна ли VM;
- доступен ли SSH;
- не изменилась ли сеть;
- не выключена ли машина;
- нет ли проблем с диском или загрузкой ОС.

Действия:

- восстановить доступ к машине;
- проверить системные логи;
- проверить Docker;
- проверить сервисы;
- убедиться, что данные на месте.

---

## 3. API не принимает эксперименты

Проверить:

- запущен ли контейнер API;
- доступен ли API снаружи;
- проходят ли запросы аутентификации;
- есть ли ошибки в логах API;
- доступна ли PostgreSQL;
- хватает ли места на диске;
- доступна ли директория загрузок.

Действия:

- посмотреть логи API;
- проверить статус PostgreSQL;
- проверить права на директории данных;
- проверить свободное место;
- перезапустить только нужный сервис, если причина понятна.

---

## 4. Валидация падает

Проверить:

- причину `validation_failed`;
- есть ли `experiment.json`;
- есть ли `signal.bin`;
- корректен ли размер бинарника;
- не выходят ли сегменты за пределы файла;
- нет ли проблем с `experiment_id`;
- не повреждён ли пакет при загрузке.

Действия:

- не исправлять эксперимент на сервере молча;
- вернуть понятную ошибку пользователю;
- при необходимости попросить повторную отправку;
- сохранить диагностическую информацию.

---

## 5. PostgreSQL не стартует

Проверить:

- контейнер PostgreSQL;
- volume PostgreSQL;
- свободное место на диске;
- логи PostgreSQL;
- права на директорию данных;
- последнее успешное состояние бэкапа.

Действия:

- не удалять volume;
- не пересоздавать БД без решения;
- снять копию текущего состояния, если это возможно;
- восстановить из бэкапа, если данные повреждены;
- после восстановления проверить API и web.

---

## 6. Диск заканчивается

Проверить:

- общий размер файлов экспериментов;
- размер результатов обработки;
- размер PostgreSQL;
- размер логов;
- размер бэкапов;
- временные файлы контейнеров.

Действия:

- не удалять эксперименты вручную без решения;
- очистить безопасные временные файлы, если они есть;
- проверить политику хранения старых бэкапов;
- перенести или расширить хранилище;
- после освобождения места проверить бэкапы и PostgreSQL.

---

## 7. Пайплайн обработки завис или падает

Проверить:

- статус эксперимента;
- логи `pipeline-worker`;
- доступность исходных файлов;
- доступность PostgreSQL;
- хватает ли CPU/RAM/диска;
- не сломались ли параметры обработки;
- не изменилась ли версия пайплайна.

Действия:

- остановить зависшую задачу, если это безопасно;
- сохранить лог ошибки;
- перевести эксперимент в понятный статус;
- повторный запуск делать вручную после понимания причины;
- исходные файлы не изменять.

---

## 8. Web не открывается

Проверить:

- контейнер web;
- доступность API;
- аутентификацию пользователя;
- сетевой вход;
- логи web;
- ошибки браузера;
- доступность PostgreSQL, если web читает статусы через API.

Действия:

- перезапустить web, если причина в контейнере;
- проверить API;
- проверить сертификаты и входной proxy, если они появятся;
- убедиться, что проблема не в правах пользователя.

---

## 9. Бэкап не выполняется

Проверить:

- расписание бэкапа;
- логи backup job;
- доступность PostgreSQL;
- доступность файлового хранилища;
- права на директорию бэкапов;
- свободное место;
- возраст последнего успешного бэкапа.

Действия:

- исправить причину сбоя;
- запустить бэкап вручную;
- проверить, что новый бэкап появился;
- проверить мониторинг;
- при длительном сбое считать систему работающей с повышенным риском.

---

## 10. Обновление прошло неудачно

Проверить:

- какая версия была до обновления;
- какие контейнеры обновлялись;
- были ли миграции БД;
- есть ли свежий бэкап;
- какие healthcheck не прошли;
- какие ошибки в логах.

Действия:

- если БД не менялась, откатить контейнеры к предыдущей версии;
- если БД менялась, действовать по процедуре миграций и восстановления;
- проверить API, web, PostgreSQL, пайплайн и бэкапы;
- зафиксировать причину неудачного обновления.

---

## 11. Полное восстановление сервера

Сценарий нужен, если VM потеряна или сервер нужно поднять на новой машине.

Общий порядок:

1. Подготовить новую Ubuntu VM.
2. Запустить Ansible для базовой настройки.
3. Установить Docker и конфигурацию сервисов через Ansible.
4. Восстановить PostgreSQL из бэкапа.
5. Восстановить файловое хранилище экспериментов.
6. Восстановить конфигурации мониторинга.
7. Запустить сервисы.
8. Проверить API, web, PostgreSQL, пайплайн.
9. Проверить, что эксперименты видны в веб-интерфейсе.
10. Проверить, что бэкапы снова выполняются.
