# infra_overview.md

## Инфраструктурный слой

Инфраструктурный слой описывает, как серверное звено реально живёт в
эксплуатации: где оно разворачивается, как обновляется, как наблюдается, как
восстанавливается после сбоев и как защищаются данные экспериментов.

Это не отдельное функциональное звено передачи данных. Первое звено — Flutter-
приложение, второе звено — серверная часть. Инфраструктурный слой является
операционной оболочкой второго звена.

Текущий этап: локальная Ubuntu VM, доступ по SSH, развёртывание и отладка всей
серверной части в контролируемой среде. Позже эта же схема должна переноситься
туда, куда руководство лаборатории решит разместить сервер.

---

## Сквозные принципы

1. **Инфраструктура служит эксплуатации, а не галочке.** Каждый инструмент
   добавляется только тогда, когда он решает реальную задачу: воспроизводимость,
   обновления, мониторинг, бэкапы, восстановление.

2. **Система должна быть переносимой.** Сервер может жить сначала на локальной
   VM, затем на физическом сервере или другой площадке. Поэтому конфигурация не
   должна быть привязана к одному ручному состоянию машины.

3. **Исходные данные экспериментов важнее удобства деплоя.** `signal.bin`,
   `experiment.json`, результаты обработки и PostgreSQL должны переживать
   перезапуски, обновления и пересборки контейнеров.

4. **Развёртывание должно быть повторяемым.** Один и тот же набор шагов должен
   поднимать сервер из чистой Ubuntu VM до рабочего состояния.

5. **Сбои должны быть видимыми.** Ошибка API, БД, пайплайна, диска, бэкапа или
   загрузки эксперимента должна попадать в мониторинг и логи.

6. **Восстановление важнее самого факта бэкапа.** Бэкап считается полезным только
   если понятно, как из него восстановиться и это периодически проверяется.

---

## 1. Состав инфраструктурного слоя

Инфраструктурный слой состоит из следующих блоков:

- `linux.md` — базовая серверная среда: Ubuntu, SSH, пользователи, права,
  firewall, директории.
- `docker.md` — контейнеризация серверных сервисов, volume, сети и правила
  хранения данных.
- `ansible.md` — повторяемая подготовка сервера и развёртывание приложения.
- `ci_cd.md` — доставка изменений, сборка, деплой, откат.
- `monitoring.md` — Prometheus, Grafana, метрики, алерты, наблюдаемость.
- `backup.md` — резервное копирование файлов экспериментов и PostgreSQL.
- `runbook.md` — эксплуатационные сценарии и действия при типовых сбоях.

---

## 2. Базовый порядок внедрения

1. Подготовить Ubuntu VM и доступ по SSH.

2. Развернуть серверную часть вручную достаточно один раз, чтобы понять реальные
   требования к директориям, портам, переменным окружения и volume.

3. Описать это состояние через Docker Compose.

4. Перенести подготовку сервера и деплой в Ansible.

5. Добавить CI/CD для безопасного обновления.

6. Подключить мониторинг и алерты.

7. Настроить бэкапы и проверить восстановление.

8. Описать runbook для типовых эксплуатационных ситуаций.

---

## 3. Что должно быть развёрнуто

Минимальный состав серверного стенда:

- сервер/API приёма экспериментов;
- блок валидации;
- PostgreSQL;
- файловое хранилище экспериментов;
- пайплайн обработки в Docker-контейнерах;
- веб-интерфейс;
- Prometheus;
- Grafana;
- механизм бэкапов;
- логи и технические статусы.

Конкретные фреймворки приложения и детали реализации фиксируются позже. На этом
уровне важно, что инфраструктура должна обслуживать все блоки второго звена.

---

## 4. Что пока не используем

На текущем этапе не используем:

- Kubernetes;
- Terraform;
- сложную облачную инфраструктуру;
- распределённое хранилище;
- автоматическое масштабирование.

Эти инструменты появятся позже, когда будет реальное место размещения сервера,
реальные требования к отказоустойчивости и понятная боль, которую они решают.
Сейчас базовая цель — надёжная, понятная и переносимая серверная система на VM.

---

## 5. Результат этапа

Этап инфраструктуры считается закрытым, когда:

- сервер можно поднять на чистой Ubuntu VM по инструкции и Ansible;
- сервисы запускаются через Docker;
- данные лежат вне контейнеров;
- обновление выполняется предсказуемо;
- есть мониторинг состояния системы;
- есть бэкапы PostgreSQL и файлов экспериментов;
- восстановление из бэкапа проверено;
- есть runbook для типовых сбоев.
