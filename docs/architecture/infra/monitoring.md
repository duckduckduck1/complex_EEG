# monitoring.md

## Мониторинг

Мониторинг нужен, чтобы система была наблюдаемой: видно ли, что сервер жив,
принимает ли он эксперименты, работает ли PostgreSQL, хватает ли места на диске,
запускается ли пайплайн, выполняются ли бэкапы.

На схеме мониторинг расположен поверх серверной части, потому что он должен
наблюдать не один блок, а всю операционную систему второго звена.

---

## Сквозные принципы

1. **Мониторинг отвечает на вопрос "система здорова или нет".** Он должен
   показывать состояние сервисов, данных и фоновых задач.

2. **Алерты нужны только на реальные проблемы.** Слишком шумный мониторинг
   перестаёт быть полезным.

3. **Бэкапы тоже мониторятся.** Недостаточно настроить расписание, нужно знать,
   что бэкап действительно выполнился.

4. **Метрики дополняют логи.** Метрики показывают состояние, логи помогают
   разобраться в причине.

---

## 1. Инструменты

Базовый набор:

- Prometheus для сбора метрик;
- Grafana для дашбордов;
- exporters для системных и сервисных метрик;
- алерты для критичных состояний.

Конкретные exporters и способ доставки алертов фиксируются позже.

---

## 2. Что мониторим

Системный уровень:

- доступность сервера;
- CPU;
- RAM;
- свободное место на диске;
- inode, если потребуется;
- состояние Docker;
- перезапуски контейнеров.

Сервисный уровень:

- API доступен;
- web доступен;
- PostgreSQL доступен;
- валидатор работает;
- пайплайн запускается;
- очередь обработки не застряла;
- Prometheus и Grafana работают.

Данные и фоновые задачи:

- успешность загрузок экспериментов;
- ошибки загрузок;
- ошибки валидации;
- ошибки обработки;
- длительность обработки;
- успешность бэкапов;
- возраст последнего успешного бэкапа;
- размер хранилища экспериментов.

---

## 3. Дашборды

Минимальные дашборды:

1. **Общее состояние сервера**
   - CPU;
   - RAM;
   - диск;
   - контейнеры;
   - uptime.

2. **Состояние приложения**
   - API;
   - web;
   - загрузки экспериментов;
   - ошибки валидации;
   - статусы обработки.

3. **PostgreSQL**
   - доступность;
   - размер БД;
   - подключения;
   - ошибки.

4. **Пайплайн**
   - количество задач;
   - успешные обработки;
   - ошибки обработки;
   - длительность обработки.

5. **Бэкапы**
   - последний успешный бэкап PostgreSQL;
   - последний успешный бэкап файлов;
   - ошибки бэкапов;
   - размер бэкапов.

---

## 4. Алерты

Критичные алерты:

- сервер недоступен;
- API недоступен;
- PostgreSQL недоступен;
- диск почти заполнен;
- контейнер постоянно перезапускается;
- бэкап не выполнялся дольше допустимого времени;
- пайплайн массово падает;
- загрузки экспериментов регулярно завершаются ошибкой.

Некритичные предупреждения:

- диск постепенно заполняется;
- растёт очередь обработки;
- увеличивается время обработки;
- растёт число ошибок валидации.

---

## 5. Логи

Логи нужны для расшифровки инцидентов:

- API: кто и когда загружал, какие ошибки были;
- валидатор: причины отказа;
- пайплайн: этапы и ошибки обработки;
- web: ошибки доступа;
- PostgreSQL: ошибки БД;
- backup: успешные и неуспешные бэкапы;
- system/docker: перезапуски и системные сбои.

На текущем этапе достаточно понятной стратегии просмотра логов. Централизованный
лог-стек можно добавить позже, если появится реальная необходимость.

---

## 6. Что не входит в мониторинг

- исправление ошибок автоматически без решения оператора;
- замена runbook;
- хранение исходных данных;
- анализ научного качества ЭЭГ;
- автоматическая разметка;
- ML/MLOps.
