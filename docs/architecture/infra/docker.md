# docker.md

## Docker

Docker используется для упаковки и запуска серверных сервисов. Он делает
окружение воспроизводимым: приложение, веб-интерфейс, пайплайн обработки,
мониторинг и вспомогательные сервисы запускаются одинаково на VM и на будущей
серверной площадке.

На текущем этапе базовый инструмент оркестрации — Docker Compose. Kubernetes
появится позже, только если возникнет реальная необходимость.

---

## Сквозные принципы

1. **Контейнеры одноразовые, данные постоянные.** Контейнер можно пересобрать и
   удалить. Данные экспериментов, PostgreSQL и результаты обработки должны жить в
   volume или на хостовой файловой системе.

2. **Каждый сервис имеет понятную ответственность.** API, БД, пайплайн, web,
   мониторинг и бэкапы не смешиваются в один контейнер.

3. **Конфигурация передаётся явно.** Переменные окружения, volume и сети должны
   быть описаны в compose/Ansible, а не настраиваться руками внутри контейнера.

4. **Секреты не попадают в образ.** Пароли, токены и ключи не должны быть
   зашиты в Dockerfile или репозиторий.

---

## 1. Сервисы в контейнерах

Предполагаемый состав:

- `api` — сервер приёма экспериментов, статусов и связи с приложением;
- `web` — веб-интерфейс для коллег;
- `postgres` — PostgreSQL;
- `validator` — проверка пакетов экспериментов, если выделяется отдельно;
- `pipeline-worker` — обработка экспериментов;
- `prometheus` — сбор метрик;
- `grafana` — дашборды;
- `backup` или backup job — задачи резервного копирования, если реализуются
  контейнером.

Точное разделение сервисов фиксируется позже на этапе реализации. На
архитектурном уровне важно, что данные и обязанности не смешиваются.

---

## 2. Volume и данные

Постоянные данные:

- PostgreSQL data volume;
- директория исходных экспериментов;
- директория результатов обработки;
- директория логов;
- директория бэкапов;
- конфигурация Grafana/Prometheus, если она должна переживать пересоздание
  контейнеров.

Внутри контейнера нельзя хранить единственную копию ценных данных. Пересборка
образа или удаление контейнера не должны приводить к потере экспериментов.

---

## 3. Сети

Нужно разделять:

- публичный вход к API/web;
- внутреннюю сеть между API, PostgreSQL, валидатором и пайплайном;
- доступ мониторинга к сервисам;
- доступ к PostgreSQL только из нужных контейнеров.

PostgreSQL по умолчанию не публикуется наружу. Веб-интерфейс и API публикуются
только через выбранный входной слой.

---

## 4. Образы

Образы должны собираться воспроизводимо:

- исходный код приложения;
- зависимости;
- версия runtime;
- настройки запуска;
- healthcheck, если применимо.

Образ не должен содержать:

- пользовательские данные;
- эксперименты;
- бэкапы;
- секреты;
- локальные временные файлы разработчика.

---

## 5. Обновления контейнеров

Обновление контейнера должно проходить предсказуемо:

1. собрать или получить новый образ;
2. проверить конфигурацию;
3. остановить старый контейнер;
4. запустить новый контейнер с теми же volume;
5. проверить healthcheck;
6. убедиться, что данные доступны;
7. при ошибке откатиться к предыдущей версии.

Перед обновлениями, которые затрагивают БД или формат данных, нужен актуальный
бэкап.

---

## 6. Логи контейнеров

Каждый сервис должен писать логи так, чтобы их можно было собрать и посмотреть:

- API: загрузки, ошибки, статусы;
- валидатор: ошибки структуры данных;
- пайплайн: этапы обработки и сбои;
- web: ошибки доступа и интерфейса;
- PostgreSQL: ошибки БД;
- backup: успешность и сбои бэкапов.

Логи нужны для runbook и мониторинга.

---

## 7. Что не входит в Docker-слой

- ручное хранение данных внутри контейнера;
- запуск всех сервисов в одном контейнере;
- хранение секретов в образе;
- Kubernetes на текущем этапе;
- бизнес-логика обработки ЭЭГ.
