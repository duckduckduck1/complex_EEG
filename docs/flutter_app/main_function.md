# Главный модуль и запуск

## Основные функции приложения для сбора и разметки ЭЭГ

Десктопное Flutter-приложение (Windows). Рабочее место экспериментатора:
принимает сигнал ЭЭГ с устройства по BLE, отображает его, позволяет размечать
поведение животного, управляет фотобиомодуляцией и формирует самодостаточный
файл эксперимента для последующей обработки на сервере.

**Аппаратная база:** одноканальное устройство на чипе MAX30003 (ECG AFE, 18-бит
АЦП), sample rate = 250 sps. Данные приходят по BLE пакетами (33 байта = 11
значений амплитуды; каждое значение — 3 байта, склеиваемые в приложении из уже
валидных данных). Приложение преобразует каждое значение в амплитуду в мкВ и
сохраняет обработанное значение как int32.

---

## Сквозные принципы

Эти принципы определяют все решения ниже:

1. **Записываем точно то, что знаем точно; помечаем явно то, чего не знаем;**
   Точное время отсчётов — из sample rate.
   Длина разрыва связи — приблизительно, по часам ноутбука, помечается как
   приблизительная. Стык после разрыва — это не данные, а явно обозначенная дыра.
   Все индексы отсчётов считаются с нуля. Диапазоны сегментов задаются как
   полуоткрытые интервалы [start_sample, end_sample): начало входит, конец не
   входит.

2. **Каждая функция служит либо созданию части файла эксперимента
   (сигнал + сегменты + разметка + события + метаданные), либо его надёжной
   доставке на сервер.** Если функция не делает ни того, ни другого — она лишняя.

3. **Сегмент задаётся только обрывами связи, никогда — разметкой.** Разметка
   ложится поверх сегментов.

4. **Разделяй потоки данных по частоте и критичности.** Частый, но
   некритичный поштучно поток (сигнал) — буферизуется и пишется редко пачками.
   Редкий, но критичный поток (события) — пишется немедленно. Так надёжность и
   производительность перестают конфликтовать.

---

## Работа с BLE

1.1. Поиск устройств
1.2. Подключение к устройству
1.3. Работа с несколькими устройствами одновременно: каждое устройство ведёт
     отдельный независимый эксперимент
1.4. Обработка ошибок подключения + автосохранение данных до сбоя
1.5. Память ранее подключённых устройств (не искать заново каждый раз)
1.6. **Ручное** переподключение при обрыве (НЕ автоматическое — оператор видит
     обрыв и контролирует его)

## Запись эксперимента

2.1. Старт / стоп записи
2.2. Преобразование каждого значения амплитуды из 3 байт (как приходит с
     устройства) в значение амплитуды в мкВ при приёме — на диск пишутся уже
     готовые int32 в единицах мкВ
2.3. Идентификация эксперимента (уникальное имя/ID)
2.4. Индикатор статуса: идёт / на паузе / остановлена, длительность, объём данных
2.5. Контроль свободного места, предупреждение заранее
2.6. Восстановление прерванной записи после краша приложения/системы по
     фактическому размеру бинарника и append-only журналу событий
2.7. Время каждого отсчёта внутри сегмента = T0 сегмента +
     segment_sample_index / 250 (от устройства, не от часов ноутбука; кварц
     32.768 кГц стабилен)

## Архитектура записи на диск  ← критично для надёжности и производительности

Два независимых потока, каждый пишется по-своему:

3.1. **Сигнал (бинарник) — буферизованная запись.** Отсчёты копятся в буфере в
     памяти и сбрасываются на диск пачкой **раз в 10 секунд** (интервал
     настраивается — на слабых ПК реже дёргаем диск, ниже нагрузка). Запись
     append-only (только дозапись в конец). При крахе теряется максимум последний
     интервал сигнала (≤10 с) — для эксперимента некритично.
3.2. **События (журнал) — немедленная запись.** Метка, обрыв, старт/конец
     сегмента, ФБМ записываются в журнал **сразу при возникновении**, append-only.
     Для самых критичных событий (обрыв, граница сегмента) — с принудительным
     сбросом на физический диск (flush/sync), чтобы пережить ребут/потерю питания.
     Событий мало, поэтому мгновенная запись не вредит производительности.
3.3. **Отрисовка графика читает из буфера в памяти, НЕ с диска.** Запись на диск
     и визуализация физически разведены — сколько бы ни писалось в фоне, график
     остаётся плавным.
3.4. **Каждое устройство = независимый эксперимент и независимый «писатель»**
     (свой буфер, свой бинарник, свой журнал, своя папка эксперимента).
     Эксперименты изолированы: сбой/отвал одного устройства не влияет на запись
     остальных. Критично при работе с несколькими устройствами.
3.5. Финальный JSON-файл эксперимента собирается из журнала по окончании записи.
3.6. **Восстановление после краша.** При запуске приложение проверяет
     фактический размер бинарника, вычисляет число реально сохранённых int32,
     сверяет его с журналом и не переносит в финальный JSON события/метки,
     которые ссылаются на отсчёты за пределами сохранённого сигнала без явной
     пометки. Незавершённый сегмент закрывается на последнем реально сохранённом
     отсчёте. Пользователь видит восстановленное состояние и решает: продолжить
     запись или завершить эксперимент.

## Сегменты и обработка разрыва  ← ядро системы

4.1. Эксперимент = последовательность **сегментов** (непрерывных кусков сигнала
     между обрывами связи)
4.2. При обрыве: пауза записи → закрытие текущего сегмента → ожидание ручного
     переподключения оператором → открытие нового сегмента
4.3. Фиксация границы: время последней точки до обрыва (точное, по sample rate).
     Граница пишется в журнал немедленно как global_sample_index в бинарнике и
     segment_sample_index внутри текущего сегмента (см. 3.2)
4.4. Настенное время паузы и возобновления (по часам ноутбука) — как
     **справочная** информация о длине разрыва, без претензии на точность
4.5. Явный маркер разрыва «здесь сигнал отсутствует» — стык никогда не выдаётся
     за непрерывный сигнал; сегменты НЕ склеиваются встык
4.6. Один бинарник на эксперимент: после переподключения запись продолжается в
     **тот же** бинарник, границы сегментов и разрывы фиксируются в JSON/журнале

**Контекст (Сценарий Б):** устройство стримит постоянно и не буферизует данные
для приложения — при обрыве сигнал за время разрыва теряется безвозвратно.
Поэтому единственное окно потери — разрыв BLE, и задача приложения — не потерять
*время*, даже когда потерян *сигнал*.

## Визуализация

5.1. График сигнала в мкВ в реальном времени
5.2. Live-сигнал с устройства отображается ТОЛЬКО в режиме активной записи
     (защита от потери данных + от иллюзии «думал, что пишу, а запись не шла»).
     Сохранённые эксперименты отображаются отдельно в режиме просмотра/доразметки
5.3. Масштаб по времени и амплитуде (приблизить / отдалить)
5.4. Прокрутка по уже записанному участку, не прерывая запись
5.5. Отображение меток, событий и разрывов прямо на графике

## Разметка  ← сердце для будущего ML

6.1. Метки-**состояния** (интервальные, с началом и концом): сон, покой/сидит,
     еда, груминг/умывается, локомоция/бегает и т.д.
6.2. Метки-**события** (точечные, в моменте времени)
6.3. Свободный ручной ввод для необычного (с привязкой ко времени)
6.4. Привязка любой метки к **(segment_id + segment_sample_index)**. Интервальная
     метка **не может пересекать границу сегмента**: если состояние длится через
     обрыв, оно завершается на конце одного сегмента и начинается заново в
     следующем (внутри разрыва наблюдения нет — не достраиваем). Точечные события
     и состояния — разные слои, во времени могут совпадать свободно.
6.5. Редактирование / удаление метки
6.6. Доразметка сохранённой записи (открыть эксперимент и разметить позже)
6.7. Словарь состояний/событий вынесен в **настраиваемый справочник**, а не зашит
     в код (словарь будет меняться; согласование его состава — научная задача
     лаборатории, блокер для будущего ML)
6.8. Маркировка участков «брак / исключить из анализа»

## Метаданные эксперимента

7.1. Форма перед стартом: животное, условия, цель опыта, оператор, дата
7.2. Параметры записи: sample_rate (250), модель АЦП (MAX30003, 18 бит),
     усиление/фильтры, версия прошивки устройства
7.3. Привязка метаданных к файлу эксперимента

## Фотобиомодуляция

8.1. Кнопка включения (команда на устройство по BLE)
8.2. Фиксация события стимуляции в записи с меткой времени (как точечное событие
     в сегменте; пишется в журнал немедленно)
8.3. Параметры стимуляции, если есть (длительность, интенсивность) — тоже
     записывать
8.4. Запрет включения ФБМ, пока запись на паузе из-за обрыва (нет смысла
     стимулировать, когда сигнал не пишется)

## Контроль качества данных

9.1. Индикатор качества сигнала в реальном времени
9.2. Предупреждение о пропаже сигнала / аномалиях
9.3. Маркировка «исключить из анализа» (см. 6.8)

## Работа с сохранёнными экспериментами

10.1. Список записанных экспериментов
10.2. Открыть запись для просмотра / доразметки
10.3. Экспорт в формат «файл эксперимента» (контракт с сервером)
10.4. Проверка готовности пакета к загрузке через Web UI:
      готов / не готов / ошибка экспорта
10.5. Подготовка папки или архива эксперимента для ручной загрузки через Web UI
10.6. Локальная папка эксперимента не удаляется автоматически после успешной
      загрузки на сервер; удаление или архивирование выполняется только вручную


## Формат файла эксперимента

**Файл эксперимента = бинарник сигнала + JSON-описание** (папка на эксперимент).

**Бинарник (один на эксперимент):** подряд идущие обработанные значения амплитуды
в мкВ, int32, по сегментам. Только числа амплитуды — компактно и быстро читается.
(~3.4 МБ на час записи при 250 sps; ~1.2 ГБ в год при часе записи в день —
объёмы некритичны, сжатие не требуется.)

**JSON (человекочитаемое описание, собирается из журнала):**
- **метаданные**: ID эксперимента, дата/время старта, животное, оператор, цель
- **параметры записи**: sample_rate=250, фильтры
- **сегменты**: список; у каждого — время старта (настенное), start_sample и
  end_sample в бинарнике как полуоткрытый диапазон [start_sample, end_sample),
  длительность
- **разрывы**: между какими сегментами, приблизительная длина (по часам ноутбука),
  пометка «сигнал отсутствует»
- **разметка**: состояния (segment_id + start_sample/end_sample внутри сегмента
  + тип), события (segment_id + segment_sample_index + тип), свободный текст,
  бракованные участки
- **события ФБМ**: segment_id + segment_sample_index + параметры

**Ключевой принцип формата:** JSON ссылается на бинарник по номерам отсчётов,
время вычисляется из sample_rate, разметка привязана к
(segment_id + segment_sample_index). Поэтому при разрыве ничего не «плывёт»:
бинарник — только цифры, всё остальное знание — в JSON.

**Во время записи** ведётся append-only журнал событий (старты сегментов, метки,
обрывы, ФБМ), который растёт по ходу и переживает краш. Финальный аккуратный JSON
собирается из этого журнала по завершении эксперимента.
