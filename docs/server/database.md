# Хранилище данных (PostgreSQL и файлы)

## Хранилище данных

Блок `data_base.md` описывает серверное хранилище данных. На схеме он может быть
подписан как база данных, но по смыслу это два связанных слоя: файловое хранилище
исходных экспериментов и PostgreSQL для метаданных, статусов и результатов.

Исходные файлы эксперимента не должны храниться как обычные поля PostgreSQL.
PostgreSQL хранит карточки, связи, статусы и ссылки на файлы, а сами файлы
остаются в файловом хранилище.

---

## Сквозные принципы

1. **Исходный пакет эксперимента неизменяем.** `signal.bin` и `experiment.json`
   сохраняются как первичный источник данных.

2. **Файлы и метаданные разделены.** Крупные бинарные данные лежат в файловом
   хранилище, а PostgreSQL хранит структуру, статусы и ссылки.

3. **Производные результаты не заменяют исходные данные.** Любая обработка
   создаёт отдельные результаты.

4. **Хранилище должно бэкапиться.** Бэкап файлов и бэкап PostgreSQL — разные, но
   согласованные задачи.

---

## 1. Файловое хранилище

Файловое хранилище содержит исходные пакеты экспериментов:

- `signal.bin`;
- `experiment.json`;
- `journal.ndjson`, если отправлен;
- `app.log`, если отправлен.

Также файловое хранилище может содержать производные результаты обработки:

- обработанные сигналы;
- отчёты;
- графики;
- таблицы признаков;
- архивы результатов пайплайна.

Структура хранения фиксируется позже на этапе реализации. На уровне архитектуры
важно, что каждый эксперимент имеет отдельную директорию или отдельный
изолированный путь хранения.

---

## 2. PostgreSQL

PostgreSQL хранит служебные данные:

- карточку эксперимента;
- `experiment_id`;
- пользовательское название эксперимента;
- дату и время загрузки;
- оператора, животное, цель опыта и другие метаданные;
- текущий статус эксперимента;
- результат валидации;
- ошибки валидации;
- статус обработки;
- ошибки обработки;
- ссылки на исходные файлы;
- ссылки на результаты обработки;
- историю ключевых событий на сервере.

PostgreSQL не является местом для хранения основного бинарного сигнала.

---

## 3. Статусы в хранилище

Для каждого эксперимента хранится текущий статус:

- `uploading`;
- `uploaded`;
- `validating`;
- `accepted`;
- `validation_failed`;
- `processing`;
- `processed`;
- `processing_failed`.

История смены статусов полезна для диагностики и разбора инцидентов, поэтому её
желательно хранить отдельно от текущего статуса.

---

## 4. Связь с валидацией

После успешной валидации:

- исходные файлы сохраняются в файловом хранилище;
- в PostgreSQL создаётся или обновляется карточка эксперимента;
- эксперимент получает статус `accepted`;
- сервер может запускать пайплайн обработки.

После неуспешной валидации:

- эксперимент получает статус `validation_failed`;
- причина ошибки сохраняется;
- пайплайн обработки не запускается;
- пользователь может увидеть ошибку через приложение или веб-интерфейс.

---

## 5. Связь с пайплайном обработки

Пайплайн обработки читает исходные данные из хранилища и записывает результаты
обратно:

- файлы результатов сохраняются в файловом хранилище;
- ссылки, статусы и краткое описание результатов сохраняются в PostgreSQL;
- исходный пакет эксперимента не изменяется.

Веб-интерфейс читает карточки, статусы и ссылки из PostgreSQL, а файлы и
результаты получает через сервер.

---

## 6. Бэкапы

Нужны два типа бэкапов:

1. **Бэкап файлов экспериментов.** Защищает `signal.bin`, `experiment.json` и
   производные результаты.

2. **Бэкап PostgreSQL.** Защищает метаданные, статусы, ссылки и историю
   обработки.

Бэкапы выполняются по расписанию. Их успешность должна попадать в мониторинг.

---

## 7. Что не входит в этот блок

- live-запись сигнала;
- валидация структуры эксперимента;
- запуск обработки;
- отображение веб-интерфейса;
- автоматическая разметка;
- ML/MLOps.
